Supabase Auth and Seamless Auth are both open source auth servers backed by Postgres, and both can
be self-hosted or used as a hosted service. They are aimed at different shapes of application.
Supabase Auth (the Go server formerly called GoTrue) is one part of the Supabase platform: it stores
users in your Supabase Postgres database and issues JWTs that Supabase's APIs and Postgres Row Level
Security (RLS) policies consume. Seamless Auth is a standalone, passwordless-only auth server that
sits behind your own backend, built around passkeys.

This page is for an engineer choosing between the two. Supabase details were checked against
Supabase's official docs, pricing page, changelog, and GitHub as of October 2026, and each one links
to its source at the bottom. Seamless Auth details were checked against the source repositories.
Supabase's passkey support in particular has changed during 2026, so check its docs for the current
status.

---

## Choose Supabase Auth If

- **You are building on Supabase.** If your data already lives in Supabase Postgres and you use its
  client libraries and RLS, Supabase Auth is the integrated choice: `auth.uid()` in an RLS policy,
  the user in the same database, one client, one dashboard. Seamless Auth does not integrate with
  RLS.
- **You need password sign-in.** Supabase Auth supports passwords. Seamless Auth has no password
  flow, by design.
- **You need SAML enterprise SSO.** Supabase Auth supports SAML 2.0 on the Pro plan and above, with
  one connection per customer organization, and documents a self-hosted SAML setup. Seamless Auth
  has no SAML.
- **You want a large, established platform and ecosystem.** Supabase has official clients for
  JavaScript, Flutter, Swift, and Python, a large community, and a SOC 2 Type 2 report and HIPAA BAA
  on its Team and Enterprise plans. Seamless Auth is 0.x, with a smaller community and no
  third-party attestations.
- **You want a long list of social providers out of the box.** Supabase lists about twenty social
  providers, plus custom OAuth and OIDC providers. Seamless Auth has CLI presets for four and manual
  configuration for others.

## Choose Seamless Auth If

- **Passkeys are your primary sign-in method and you want them out of beta.** As of October 2026
  Supabase documents passkey support as experimental: the JavaScript client needs
  `experimental: { passkey: true }`, the API may change without notice, and a user must already have
  a confirmed account and be signed in to register a passkey. In Seamless Auth passkeys are the core
  flow, and the `phishing_resistant_only` setting can make them the only way to sign in.
- **Your data does not live in Supabase.** Supabase Auth is designed around Supabase Postgres and
  its API gateway. Seamless Auth stores its own data in its own Postgres and works with whatever
  database and backend your app already uses.
- **You need organizations and memberships as a built-in model.** Seamless Auth ships organizations,
  memberships, scoped roles, and an active organization on the session. In Supabase you model tenants
  yourself in tables and enforce them with RLS (Supabase's own "organizations" are for billing your
  Supabase account, not for your end users).
- **You want sign-in to go through your backend.** Seamless Auth clients call your backend's `/auth`
  routes, and browsers hold the session only in `httpOnly` cookies. Supabase clients typically talk
  to Supabase directly from the browser or app with a public key.

## Architecture Difference

**Supabase Auth** is one service in the Supabase stack. Clients call it (usually through
`supabase-js`) via the Supabase API gateway, it writes users and sessions to the `auth` schema of
the project's Postgres, and it issues JWTs that Supabase's data APIs pass through to Postgres, where
RLS policies read the user's id and claims. The auth server is open source and can run on its
own, but its design, docs, and dashboard assume the rest of Supabase. Self-hosting means running the
Supabase stack with Docker Compose, without some hosted features such as the Management API.

**Seamless Auth** is a standalone service your backend fronts:

```txt
browser or native app
  -> your backend's /auth routes   (@seamless-auth/express, fastify, nextjs, or the Python/Go/Rust adapter)
  -> seamless-auth-api             (your infrastructure, or Seamless managed)
  -> Postgres (auth data only)
```

Your backend mounts adapter routes, forwards calls with a service token, keeps browser sessions in
signed `httpOnly` cookies, and verifies sessions against the auth API's JWKS. Authorization is
enforced in your application code, not in database policies. Your application data can live in any
database. See [What Is Seamless Auth?](/start/overview#how-the-pieces-connect).

If you use Supabase for your database but want Seamless Auth for sign-in, note that Supabase's RLS
helpers expect Supabase-issued JWTs; you would enforce access in your backend instead, or do the
integration work to map Seamless Auth sessions into your database policies yourself.

## Migrating From Supabase Auth

Supabase stores users in the `auth.users` table of your own Postgres, so you can export them with a
SQL query. Seamless Auth does not import password hashes, because it has no password flow. A
migration imports identities (email, external id, phone, roles, organization memberships) with
`seamless migrate csv`, then gets each user onto a passkey through enrollment prompts and invites.
Seamless Auth imports no credentials of any kind, so existing passkeys and MFA factors do not carry
over; each user verifies their email once and enrolls a new passkey.

Follow [Migrate Users From Another Identity System](/operate/migrate-users); the
[Auth0 migration guide](/operate/migrate-from-auth0) shows the full pattern for one provider.
Fells Code, which maintains Seamless Auth, offers hands-on migration help (see the end of that
guide).
