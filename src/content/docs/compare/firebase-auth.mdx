Firebase Authentication and Seamless Auth both sign users in to your applications. Firebase
Authentication is a Google-operated service with client SDKs for Apple platforms, Android, the
web, C++, Unity, and Flutter, a drop-in UI library (FirebaseUI), and sign-in with passwords, email
links, phone numbers, anonymous accounts, custom tokens, and federated providers such as Google,
Apple, Facebook, Twitter, and GitHub. It integrates tightly with other Firebase services. An
optional upgrade, Firebase Authentication with Identity Platform, adds multi-factor authentication,
blocking functions, SAML and generic OpenID Connect providers, multi-tenancy, audit logging, and an
SLA, under a different pricing scheme. Seamless Auth is an open source (Apache-2.0),
passwordless-only auth server built around passkeys, which you self-host inside your own stack or
run on the Seamless Auth managed service.

This page is for an engineer or technical lead deciding whether to move off Firebase
Authentication, or whether to start on it. Every Firebase detail links to a Google page
(firebase.google.com or Google Cloud's Identity Platform docs), and the [Sources](#sources) section
gives the date each one was checked. Seamless Auth details were checked against the source
repositories at Seamless Auth API v0.19.3. Prices, plan contents, and limits change, so confirm them
on [firebase.google.com/pricing](https://firebase.google.com/pricing) and the
[Identity Platform pricing page](https://cloud.google.com/identity-platform/pricing) before you
decide.

## Choose Firebase Authentication If

- **Your app is built on Firebase.** Firebase Authentication works with the Security Rules of the
  Firebase Realtime Database and Cloud Storage, and with other Firebase services, out of the box. Seamless Auth sessions are not Firebase ID tokens; to use them with Security Rules,
  your backend would have to bridge them, for example through Firebase's custom auth system
  integration.
- **You need password sign-in or anonymous accounts.** Firebase supports email and password sign-in
  and temporary anonymous accounts that can later be upgraded to regular accounts. Seamless Auth has
  no password flow, by design, and no anonymous accounts.
- **You need SAML or many isolated tenants.** With the Identity Platform upgrade, Firebase supports
  SAML (web only, service-provider initiated) and generic OpenID Connect providers, and
  multi-tenancy: separate silos of users, identity providers, and configuration in one project.
  Seamless Auth has no SAML, and one instance has a single user directory and a single runtime
  configuration.
- **You want to run custom code inside the sign-in flow.** With the Identity Platform upgrade,
  blocking functions run before a user is created, before a user signs in, and (in Node.js) before
  an email or SMS is sent. Seamless Auth has no equivalent; that logic goes in your own backend.
- **You want mobile and game SDKs and a drop-in UI from one vendor.** Firebase ships client SDKs for
  Apple platforms, Android, web, C++, Unity, and Flutter, plus FirebaseUI. Seamless Auth's frontend
  SDKs cover React, Angular, Vue, Svelte, and React Native.
- **You need a vendor's compliance reports or an SLA.** Google lists ISO 27001, 27017, and 27018
  and SOC 1, 2, and 3 for Firebase Authentication; with Identity Platform it adds BAA coverage,
  PCI DSS scope, TISAX, and a 99.95% uptime SLA. Seamless Auth has no third-party compliance
  attestations of its own.
- **You want nothing to run yourself and a large, established product.** Google operates Firebase
  Authentication. Seamless Auth is 0.x, with a much smaller community.

## Choose Seamless Auth If

- **You want passkeys as the primary sign-in method.** As of 2026-10-21, Firebase Authentication's
  documentation lists no passkey or WebAuthn sign-in method. The only passkey mention we found on
  Google's Firebase pages is mock passkey support added to the Authentication emulator in Firebase
  CLI v15.21.0 (June 2026), a local testing tool. In Seamless Auth, passkeys are the default sign-in
  method, and the `phishing_resistant_only` setting accepts only a passkey to start a session.
- **Users and sessions must stay inside your own boundary, or outside the United States.** Google
  states that the Firebase Authentication service runs only from US data centers and processes data
  exclusively in the United States. Self-hosted, the Seamless Auth API and its Postgres database run
  wherever you deploy them.
- **You want the auth server's source under a permissive license.** The auth API, server adapters,
  frontend SDKs, admin dashboard, and CLI are all Apache-2.0. Firebase Authentication is a
  proprietary Google service.
- **You want MFA, an audit trail, and organizations without a paid upgrade.** In Firebase,
  multi-factor authentication (SMS or TOTP), audit logging, and multi-tenancy need the Identity
  Platform upgrade. Seamless Auth ships TOTP as a second factor, passkey step-up, organizations and
  memberships with per-organization roles and scopes, and an append-only, hash-chained auth event
  trail, all in the open source release.
- **You prefer not to pay per active user or per SMS.** Self-hosting has no per-user fee; you pay for
  the infrastructure you run and your own SMS provider (Twilio or AWS SNS). Identity Platform
  charges per monthly active user above its free tier, more for SAML and OIDC users, and per SMS.
- **You want your user data in a database you can query.** Self-hosted, users, memberships, and auth
  events are rows in a Postgres database you run.

## Architecture Difference

**Firebase Authentication** is a Google-operated backend that your client SDK talks to directly.
The app collects credentials (or an OAuth token from a federated provider), passes them to the
Firebase Authentication SDK, and Firebase returns an ID token. Firebase services enforce Security
Rules against that token, and your own backend can verify it. Users live in Firebase's user
database, and with Identity Platform, blocking functions can change the outcome of sign-up and
sign-in.

**Seamless Auth** is a service you run next to your backend:

```txt
browser or native app
  -> your backend's /auth routes   (@seamless-auth/express, fastify, nextjs, or the Python/Go/Rust adapter)
  -> seamless-auth-api             (your infrastructure, or Seamless Auth managed)
  -> Postgres
```

Clients never call the auth API directly. Your backend mounts the adapter routes, forwards calls
with a service token, and keeps the session in signed `httpOnly` cookies on your domain (native
apps use bearer tokens in the platform keystore). Your backend verifies sessions locally against the
auth API's JWKS. Authorization stays in your own code. See
[What Is Seamless Auth?](/start/overview#how-the-pieces-connect).

The practical consequence: Firebase Authentication is a client-first service designed to sit in
front of Firebase's own data products; Seamless Auth needs a backend of yours in the path, and the
session lives on your domain.

## When Not To Use Seamless Auth

Be direct with yourself about these before planning a move off Firebase Authentication. If any is a
hard requirement today, stay on Firebase or choose another product.

- **Your data access depends on Firebase Security Rules.** Realtime Database and Cloud Storage rules
  see Firebase-authenticated users, not Seamless Auth sessions. Moving means routing that
  access through your backend or bridging identities with custom tokens.
- **Your app has no backend.** Seamless Auth's clients go through a server adapter in your backend;
  there is no direct client-to-auth-server mode.
- **Your users sign in with passwords, or you rely on anonymous accounts.** Neither exists in
  Seamless Auth, and no password hashes are imported.
- **A customer requires SAML SSO into your app, or you need tenants with separate configuration.**
  Seamless Auth has no SAML and no multi-tenancy. Its OAuth and OpenID Connect providers are
  configured instance-wide.
- **You depend on blocking functions to shape tokens or gate sign-in.** There is no hook system; you
  move that logic into your backend.
- **You need a vendor's SOC 2 report, BAA, or SLA for the auth service itself.** Seamless Auth has no
  third-party attestations. Self-hosted, it is covered by your own controls.
- **You need a 1.0 stability guarantee.** Every Seamless Auth package is still 0.x.

The full list is in
[When Seamless Auth Is Not The Right Choice](/start/overview#when-seamless-auth-is-not-the-right-choice).

## Migrating From Firebase Authentication

There is no Firebase migration guide yet. This page does not describe a tested Firebase migration,
and you should plan one as you would any identity migration, with a dry run.

What the docs do support today is the generic identity import in
[Migrate Users From Another Identity System](/operate/migrate-users): a CSV of email, external id,
phone, roles, and organizations, imported with `seamless migrate csv`. Firebase's
`firebase auth:export` writes JSON, or a CSV with fixed column positions, holding each user's UID,
email, and phone number among other fields. Those are the kind of fields the import
reads, but the export has to be converted into the import's CSV first, and this page does not
provide that conversion. Seamless Auth imports no credentials of any kind, so the password hashes in
a Firebase export are not used (the import ignores every column it does not map), and each user
proves their email once and enrolls a new passkey. The generic guide's optional
step of signing users in through the old provider during cutover needs the old system to act as an
OpenID Connect provider for Seamless Auth; this page does not cover whether or how that applies to
Firebase.

Fells Code, which maintains Seamless Auth, offers hands-on migration help:
[fellscode.com](https://fellscode.com).
