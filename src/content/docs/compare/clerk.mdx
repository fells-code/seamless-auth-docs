Seamless Auth and Clerk both handle sign-in, sessions, and user management for web and mobile
apps, but they are built on different premises. Clerk is a hosted, proprietary authentication and
user management service with polished prebuilt components and a broad feature set, including
passwords and enterprise SSO. Seamless Auth is an open source (Apache-2.0), passwordless-only auth
server that you self-host inside your own stack or run on the Seamless Auth managed service.

This page is for an engineer deciding between the two. Competitor details were checked against
Clerk's official docs, pricing page, and GitHub as of October 2026, and each one links to its
source at the bottom of the page. Seamless Auth details were checked against the source
repositories. Prices and plan contents change, so confirm them on Clerk's pricing page before you
decide.

---

## Choose Clerk If

- **You want no auth infrastructure to run at all.** Clerk operates the service, the database,
  email and SMS delivery, and upgrades. Seamless Auth's managed path also removes this, but its
  self-hosted path, the reason most people look at it, means you operate it.
- **You need password sign-in.** Clerk supports passwords alongside passwordless methods. Seamless
  Auth has no password flow, by design.
- **You need SAML enterprise SSO or SCIM directory sync today.** Clerk offers SAML and OIDC
  enterprise connections and Directory Sync on its paid plans. Seamless Auth has neither SAML nor
  SCIM.
- **You want the most complete drop-in UI.** Clerk ships prebuilt sign-in, sign-up, user profile,
  and organization components across many SDKs, plus a hosted Account Portal.
- **You need a vendor compliance report.** Clerk lists a SOC 2 report on its Business plan and HIPAA
  with a BAA on Enterprise. Seamless Auth has no third-party compliance attestations of its own.
- **You want a 1.0-grade, widely adopted product.** Clerk has a much larger user base, ecosystem, and
  community than Seamless Auth, which is still 0.x.

## Choose Seamless Auth If

- **Users and sessions must stay inside your own boundary.** Self-hosted, the auth API and its
  Postgres database run in your infrastructure. Clerk is hosted only: its SDKs are open source, but
  the service is not, and Clerk documents no self-hosted deployment.
- **You want the auth server's source under a permissive license.** The auth API, server adapters,
  frontend SDKs, admin dashboard, and CLI are all Apache-2.0.
- **You want passwordless as the only option, enforced.** There is no password to phish or reuse.
  The `phishing_resistant_only` system setting can require passkeys for sign-in.
- **You prefer not to pay per active user for auth.** Self-hosting has no per-user fee; you pay for
  the infrastructure you run. Clerk bills per monthly retained user above its included allowance.
- **You want sign-in rendered in your own app, on your own domain, with cookies your backend
  controls.** The browser SDKs never see a token; your backend's adapter holds the session in
  `httpOnly` cookies.

## Architecture Difference

**Clerk** is an external service. Your frontend talks to Clerk's Frontend API (on a domain you
point at Clerk in production), Clerk issues the session, and your backend verifies Clerk's session
tokens with a Clerk backend SDK. Users, credentials, and organizations live in Clerk's database,
and you read them through Clerk's APIs and webhooks.

**Seamless Auth** is a service you run next to your backend:

```txt
browser or native app
  -> your backend's /auth routes   (@seamless-auth/express, fastify, nextjs, or the Python/Go/Rust adapter)
  -> seamless-auth-api             (your infrastructure, or Seamless Auth managed)
  -> Postgres
```

Clients never call the auth API directly. Your backend mounts the adapter routes, forwards calls
with a service token, and keeps the session in signed `httpOnly` cookies on your domain (native
apps use bearer tokens in the platform keystore). Your backend verifies sessions locally against the
auth API's JWKS. Authorization stays in your own code. See
[What Is Seamless Auth?](/start/overview#how-the-pieces-connect).

The practical consequence: with Clerk you integrate a vendor and its UI; with Seamless Auth you
add a service and an adapter to your own stack and own the sign-in pages.

## Migrating From Clerk

Clerk's dashboard can export users to CSV, including password hashes. Seamless Auth does not
import passwords, because it has no password flow. A migration imports identities (email, external
id, phone, roles, organization memberships) with `seamless migrate csv`, then gets each user onto a
passkey through enrollment prompts and invites. Plan for every user to verify their email once and
enroll a new passkey. Seamless Auth imports no credentials of any kind, so passkeys and MFA factors
registered with Clerk do not carry over.

Follow [Migrate Users From Another Identity System](/operate/migrate-users). The
[Auth0 migration guide](/operate/migrate-from-auth0) shows the same pattern end to end for one
provider. Fells Code, which maintains Seamless Auth, offers hands-on migration help (see the end of
that guide).
