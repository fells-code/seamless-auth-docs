[RFC 9700](https://www.rfc-editor.org/rfc/rfc9700) is the OAuth 2.0 Security Best Current
Practice. It gives recommendations for clients, for authorization servers, and for resource
servers. This page checks the Seamless Auth API against the ones that apply to it today.

Seamless Auth plays two OAuth roles:

- **Client.** When a provider is configured (Google, GitHub, Microsoft Entra ID, or any OAuth 2.0
  or OpenID Connect provider, see [OAuth Login](/build/oauth-login)), the auth API sends the user
  to that provider, exchanges the authorization code, reads the profile, and then issues its own
  Seamless Auth session. The [client recommendations](#client-recommendations) cover this.
- **Authorization server.** Since v0.21, the optional [OpenID Provider](/build/openid-provider)
  (`seamless-auth-oidc-provider`, off by default) signs other applications in and issues tokens
  for your APIs. The [authorization server recommendations](#authorization-server-recommendations)
  cover this.

The client table was written against API v0.19.2. Rows that have changed since then say so. Every
client code link points at the
[v0.19.2](https://github.com/fells-code/seamless-auth-api/tree/v0.19.2) tag of the API. The flow
lives in [`oauthService.ts`](https://github.com/fells-code/seamless-auth-api/blob/v0.19.2/src/services/oauthService.ts),
[`oauth.ts`](https://github.com/fells-code/seamless-auth-api/blob/v0.19.2/src/controllers/oauth.ts)
(the controller), and
[`oauth.routes.ts`](https://github.com/fells-code/seamless-auth-api/blob/v0.19.2/src/routes/oauth.routes.ts).

Status values:

- **Meets**: the recommendation holds by default.
- **Meets, configurable**: it holds by default, and an operator setting can turn it off.
- **Partial**: some of the recommendation holds, and the row says which part does not.
- **Not used**: the API does not use the feature the recommendation is about.

## Client Recommendations

| RFC 9700 | Recommendation | Status | How, in v0.19.2 |
| --- | --- | --- | --- |
| [2.1](https://www.rfc-editor.org/rfc/rfc9700#section-2.1), [4.7](https://www.rfc-editor.org/rfc/rfc9700#section-4.7) | Prevent CSRF: the `state` (or PKCE verifier, or OpenID Connect nonce) must be bound to the user agent that started the flow | **Meets, configurable**, since 0.19.2 | `/start` returns a random `binding` to the client that asked, never to the provider, and signs only its SHA-256 into the state ([`createOAuthState`](https://github.com/fells-code/seamless-auth-api/blob/v0.19.2/src/services/oauthService.ts#L263-L281)). The callback must present it, compared in constant time before the replay cache records the state ([`checkOAuthStateBinding`, `consumeOAuthState`](https://github.com/fells-code/seamless-auth-api/blob/v0.19.2/src/services/oauthService.ts#L305-L346)), so a state and code taken from one sign-in cannot be finished in another browser. The state is also HMAC-SHA256 signed, expires after ten minutes, and is refused on reuse. The client SDKs keep and send the binding (`@seamless-auth/client` 0.7.1 and later). `OAUTH_ALLOW_UNBOUND_STATE=true` accepts a callback with no binding while older clients are upgraded; it reopens this gap while set, warns at boot, and is removed in v0.20 ([`unboundOAuthStateAllowed`](https://github.com/fells-code/seamless-auth-api/blob/v0.19.2/src/services/oauthService.ts#L139-L157)). Version 0.19.1 and earlier did not bind the state ([#463](https://github.com/fells-code/seamless-auth-api/issues/463)). |
| [2.1](https://www.rfc-editor.org/rfc/rfc9700#section-2.1), [4.4](https://www.rfc-editor.org/rfc/rfc9700#section-4.4) | A client that uses more than one authorization server must defend against mix-up attacks, with the `iss` response parameter ([RFC 9207](https://www.rfc-editor.org/rfc/rfc9207)) or a distinct redirect URI per authorization server | **Partial** | The signed state names the provider, and a callback for another provider is refused ([`verifyOAuthState`](https://github.com/fells-code/seamless-auth-api/blob/v0.19.2/src/services/oauthService.ts#L283-L303)). That stops a state from one provider being used with another, but it does not stop the mix-up attack itself. The callback body has no `iss` and none is checked ([`FinishOAuthLoginRequestSchema`](https://github.com/fells-code/seamless-auth-types/blob/v0.29.0/src/schemas/oauth/schema.ts#L48-L53)). A provider can have its own `redirectUri`, but without one every provider shares `<first origin>/oauth/callback` ([`resolveOAuthRedirectUri`](https://github.com/fells-code/seamless-auth-api/blob/v0.19.2/src/services/oauthService.ts#L227-L247)). Every provider is configured by the operator, so the attack needs a provider the operator added to be malicious or compromised. Give each provider its own redirect URI. |
| [2.1.1](https://www.rfc-editor.org/rfc/rfc9700#section-2.1.1), [4.5](https://www.rfc-editor.org/rfc/rfc9700#section-4.5) | Prevent authorization code injection, with PKCE or the OpenID Connect nonce | **Meets, configurable** | PKCE is on unless a provider sets `pkce: false` ([`pkceEnabled`](https://github.com/fells-code/seamless-auth-api/blob/v0.19.2/src/services/oauthService.ts#L159-L161)). The verifier is derived per sign-in on the server and never leaves it, so a code stolen from one sign-in fails the exchange in another. An OpenID Connect provider also gets a nonce, signed into the state and checked against the verified ID token ([`verifyOAuthIdToken`](https://github.com/fells-code/seamless-auth-api/blob/v0.19.2/src/services/oauthService.ts#L550-L552)). A provider with `pkce: false` and no `issuer` or `jwksUri` has neither defence. Set `pkce: false` only for a provider that refuses PKCE. |
| [2.1.1](https://www.rfc-editor.org/rfc/rfc9700#section-2.1.1) | Use the `S256` PKCE challenge method | **Meets** | Only `S256` is sent ([`buildOAuthAuthorizationUrl`](https://github.com/fells-code/seamless-auth-api/blob/v0.19.2/src/services/oauthService.ts#L409-L412)). |
| [2.1.2](https://www.rfc-editor.org/rfc/rfc9700#section-2.1.2), [4.6](https://www.rfc-editor.org/rfc/rfc9700#section-4.6) | Do not use the implicit grant, or any response type that returns an access token in the authorization response | **Meets** | The authorization request always uses `response_type=code` ([`buildOAuthAuthorizationUrl`](https://github.com/fells-code/seamless-auth-api/blob/v0.19.2/src/services/oauthService.ts#L396)). Tokens come only from the token endpoint, over a back-channel request from the API. |
| [2.4](https://www.rfc-editor.org/rfc/rfc9700#section-2.4) | Do not use the resource owner password credentials grant | **Not used** | The only grant sent to a provider is `authorization_code` ([`exchangeOAuthTokens`](https://github.com/fells-code/seamless-auth-api/blob/v0.19.2/src/services/oauthService.ts#L443-L449)). Seamless Auth has no password flow. |
| [4.11](https://www.rfc-editor.org/rfc/rfc9700#section-4.11) | Do not expose an open redirector | **Meets** | A requested `redirectUri` must exactly match the provider's `redirectUris`, or, when a provider lists none, share an origin with a configured origin ([`allowedRedirect`](https://github.com/fells-code/seamless-auth-api/blob/v0.19.2/src/lib/redirectAllowlist.ts#L40-L48)). `returnTo` must share an origin with a configured origin ([`allowedReturnTo`](https://github.com/fells-code/seamless-auth-api/blob/v0.19.2/src/controllers/oauth.ts#L37-L46)), and is read back from the signed state at the callback rather than from the callback request ([`finishOAuthLogin`](https://github.com/fells-code/seamless-auth-api/blob/v0.19.2/src/controllers/oauth.ts#L178-L184)). Configure exact `redirectUris` in production. |
| [4.6](https://www.rfc-editor.org/rfc/rfc9700#section-4.6) | Validate ID tokens, so a token issued for another client or sign-in is not accepted | **Meets** | An OpenID Connect provider's ID token is checked for signature against its JWKS, issuer, audience (this client), expiry, issued-at, subject, `azp` when there are several audiences, and the nonce. Only asymmetric algorithms are accepted, so `none` and shared-key algorithms are refused ([`verifyOAuthIdToken`](https://github.com/fells-code/seamless-auth-api/blob/v0.19.2/src/services/oauthService.ts#L499-L555)). |
| [4.9](https://www.rfc-editor.org/rfc/rfc9700#section-4.9) | Send an access token only to the resource it is meant for, in a header rather than a URL | **Meets** | The provider access token is sent only to the provider's configured `userInfoUrl` (and, for GitHub, the email list on the same origin), in an `Authorization: Bearer` header ([`fetchOAuthProfile`](https://github.com/fells-code/seamless-auth-api/blob/v0.19.2/src/services/oauthService.ts#L637-L664)). An OpenID Connect provider's profile comes from the verified ID token and the access token is not used at all. |
| [4.14](https://www.rfc-editor.org/rfc/rfc9700#section-4.14) | Protect refresh tokens | **Not used** | The API reads only `access_token` and `id_token` from the provider's token response ([`exchangeOAuthTokens`](https://github.com/fells-code/seamless-auth-api/blob/v0.19.2/src/services/oauthService.ts#L468-L480)). A provider refresh token is never kept, and the provider access token is used once during the callback, then dropped. Neither is stored, logged, or returned to the client. |
| [2.2](https://www.rfc-editor.org/rfc/rfc9700#section-2.2) | Use sender-constrained access tokens (mTLS or DPoP) | **Not used** | Provider access tokens are plain bearer tokens. Each is used once, server to server, within the callback, which leaves little window for replay. DPoP and mTLS are not supported. |
| [2.3](https://www.rfc-editor.org/rfc/rfc9700#section-2.3) | Request only the privileges the client needs | **Operator setting** | The scopes sent are the provider's configured `scopes` ([`buildOAuthAuthorizationUrl`](https://github.com/fells-code/seamless-auth-api/blob/v0.19.2/src/services/oauthService.ts#L401-L403)). The API needs a subject and a verified email, so `openid email` (or the provider's equivalent, such as `user:email` on GitHub) is enough. |
| [2.5](https://www.rfc-editor.org/rfc/rfc9700#section-2.5) | Authenticate the client, preferably with an asymmetric method (mTLS or `private_key_jwt`) | **Partial** | The client authenticates with `client_secret_post` ([`exchangeOAuthTokens`](https://github.com/fells-code/seamless-auth-api/blob/v0.19.2/src/services/oauthService.ts#L437-L449)). The secret is read from the environment variable the provider's `clientSecretEnv` names, never stored in `system_config`, and never returned by the API. Asymmetric client authentication is not supported. |
| [4.2](https://www.rfc-editor.org/rfc/rfc9700#section-4.2), [4.3](https://www.rfc-editor.org/rfc/rfc9700#section-4.3) | Keep the authorization code and state out of `Referer` headers and browser history | **Application** | The provider redirects to the application's own callback page, which then posts `code` and `state` to its backend. That page is not served by the API, so this is up to the application: load no third-party content on it and leave the URL once the sign-in is finished. The code is single use at the provider and, with PKCE, useless without the verifier only the API holds. |
| [4.1](https://www.rfc-editor.org/rfc/rfc9700#section-4.1) | Use TLS for every endpoint of the flow | **Operator setting** | Provider `authorizationUrl`, `tokenUrl`, `userInfoUrl`, `issuer` and `jwksUri` must be URLs, but `http` is not refused ([provider schema](https://github.com/fells-code/seamless-auth-types/blob/v0.29.0/src/schemas/systemConfig/schema.ts#L55-L76)). Configure `https` endpoints, which every public provider uses. |
| [4.7](https://www.rfc-editor.org/rfc/rfc9700#section-4.7) | Treat a `state` as single use | **Meets**, since 0.21.0 | A consumed state is recorded in the database, so a replayed callback is refused by every API instance, not only the one that consumed it ([`consumeOAuthState`](https://github.com/fells-code/seamless-auth-api/blob/v0.21.1/src/services/oauthService.ts#L352-L373)). Callbacks no longer need sticky routing. In 0.19.2 the record lived only in the consuming instance's memory, so another instance could accept a replay inside the ten-minute window ([#414](https://github.com/fells-code/seamless-auth-api/issues/414)). |

<Aside type="note">
  Upgrade to API 0.19.2 and `@seamless-auth/client` 0.7.1 (`@seamless-auth/react` 0.18.1,
  `@seamless-auth/react-native` 0.3.3) together. With an older client, OAuth sign-in against 0.19.2
  fails with `Invalid OAuth state` unless `OAUTH_ALLOW_UNBOUND_STATE=true` is set. A direct API
  integration has to keep the `binding` from `/start` and send it with the callback.
</Aside>

## Authorization Server Recommendations

These apply to the [OpenID Provider](/build/openid-provider), which is off by default. Rows are
checked against provider 0.1.1, the version that pairs with auth API 0.21.1; provider 0.2.0 has the
same security configuration. The edge repository keeps a fuller [edge security matrix](https://github.com/fells-code/seamless-auth-oidc-provider/blob/v0.1.1/docs/oauth-security.md) that names the test behind
each row. These rows describe configuration and unit tests. They are not an OpenID certification.

| RFC 9700 | Recommendation | Status | How |
| --- | --- | --- | --- |
| [2.1](https://www.rfc-editor.org/rfc/rfc9700#section-2.1), [4.1](https://www.rfc-editor.org/rfc/rfc9700#section-4.1) | Match redirect URIs exactly against the registered value | **Meets** | Exact string match. The only exception is the port of a native app's loopback redirect, which RFC 8252 requires. The registry accepts only `https` (not `localhost`), `http` on `127.0.0.1` or `[::1]`, or a private-use scheme, with no fragments or credentials. [`oauth21.test.ts`](https://github.com/fells-code/seamless-auth-oidc-provider/blob/v0.1.1/tests/oauth21.test.ts) |
| [2.1.1](https://www.rfc-editor.org/rfc/rfc9700#section-2.1.1), [4.8](https://www.rfc-editor.org/rfc/rfc9700#section-4.8) | Support PKCE, enforce it, and prevent PKCE downgrade | **Meets, configurable** | PKCE is required for every client, and discovery lists only `S256`, so `plain` is refused. An admin can opt a confidential client out, as 2.1.1 allows; that client must then send an OpenID Connect `nonce` unless also opted out of that. A public client cannot be opted out. [`pkce.test.ts`](https://github.com/fells-code/seamless-auth-oidc-provider/blob/v0.1.1/tests/pkce.test.ts), [`oauth21.test.ts`](https://github.com/fells-code/seamless-auth-oidc-provider/blob/v0.1.1/tests/oauth21.test.ts) |
| [2.1](https://www.rfc-editor.org/rfc/rfc9700#section-2.1), [4.4](https://www.rfc-editor.org/rfc/rfc9700#section-4.4) | Return `iss` in the authorization response ([RFC 9207](https://www.rfc-editor.org/rfc/rfc9207)) | **Meets** | `iss` is on every authorization response and advertised in discovery. [`oauth21.test.ts`](https://github.com/fells-code/seamless-auth-oidc-provider/blob/v0.1.1/tests/oauth21.test.ts) |
| [2.1.2](https://www.rfc-editor.org/rfc/rfc9700#section-2.1.2), [2.4](https://www.rfc-editor.org/rfc/rfc9700#section-2.4) | Do not offer the implicit or resource owner password credentials grants | **Meets** | The only response type is `code`; `token`, `id_token` and `code id_token` are refused. The password grant is answered `unsupported_grant_type`. [`oauth21.test.ts`](https://github.com/fells-code/seamless-auth-oidc-provider/blob/v0.1.1/tests/oauth21.test.ts) |
| [2.2.2](https://www.rfc-editor.org/rfc/rfc9700#section-2.2.2), [4.14](https://www.rfc-editor.org/rfc/rfc9700#section-4.14) | Sender-constrain or rotate refresh tokens for public clients | **Meets** | Refresh tokens rotate on every use. A reused refresh token revokes the grant and ends the first-party session behind it. [`refreshAndClientCredentials.test.ts`](https://github.com/fells-code/seamless-auth-oidc-provider/blob/v0.1.1/tests/refreshAndClientCredentials.test.ts) |
| [2.3](https://www.rfc-editor.org/rfc/rfc9700#section-2.3), [4.10](https://www.rfc-editor.org/rfc/rfc9700#section-4.10) | Restrict access tokens to an audience and to the privileges granted | **Meets** | A token for an API is an RFC 9068 JWT whose `aud` is that registered resource (RFC 8707), and the auth API refuses to sign any other audience or scope. [`resourceIndicators.test.ts`](https://github.com/fells-code/seamless-auth-oidc-provider/blob/v0.1.1/tests/resourceIndicators.test.ts) |
| [2.5](https://www.rfc-editor.org/rfc/rfc9700#section-2.5) | Authenticate confidential clients, preferably with asymmetric methods | **Meets, configurable** | Confidential clients use `private_key_jwt` by default, and each assertion is single use. Shared secrets need an instance setting and a per-client opt-in. `client_secret_jwt` and HMAC algorithms are never offered. [`clientAuthentication.test.ts`](https://github.com/fells-code/seamless-auth-oidc-provider/blob/v0.1.1/tests/clientAuthentication.test.ts) |
| [4.11](https://www.rfc-editor.org/rfc/rfc9700#section-4.11), [4.12](https://www.rfc-editor.org/rfc/rfc9700#section-4.12) | Do not act as an open redirector, and do not redirect with HTTP 307 | **Meets** | Errors go only to a registered redirect URI; an unregistered one gets an error page ([`oauth21.test.ts`](https://github.com/fells-code/seamless-auth-oidc-provider/blob/v0.1.1/tests/oauth21.test.ts)). Redirects to clients use HTTP 303, the `oidc-provider` library's default. |
| [4.15](https://www.rfc-editor.org/rfc/rfc9700#section-4.15) | Keep clients from choosing a `client_id` that impersonates a resource owner | **Meets** | There is no dynamic client registration. Applications are created by an admin, and the auth API generates each client id as a random value ([`oidcApplicationService.ts`](https://github.com/fells-code/seamless-auth-api/blob/v0.21.1/src/services/oidcApplicationService.ts#L139)), so no one picks a client id. |
| [4.16](https://www.rfc-editor.org/rfc/rfc9700#section-4.16) | Prevent clickjacking of the authorization page | **Meets** | Hosted pages send `frame-ancestors 'none'` in a strict CSP. [`hostedPages.test.ts`](https://github.com/fells-code/seamless-auth-oidc-provider/blob/v0.1.1/tests/hostedPages.test.ts) |
| [4.11](https://www.rfc-editor.org/rfc/rfc9700#section-4.11) | Do not redirect to a client after a failed authentication without the user's interaction | **Meets** | Section 4.11.2's attack needs a redirect URI the attacker controls, usually registered through dynamic client registration, which is off. Redirect URIs come only from admin-registered applications, and an unregistered one gets an error page. |
| [2.6](https://www.rfc-editor.org/rfc/rfc9700#section-2.6) | Do not support CORS on the authorization endpoint | **Meets** | The authorization endpoint sends no CORS headers. Discovery and the JWKS allow any origin, since they are public metadata. Userinfo, and the token endpoint for public clients, allow only an origin among the client's registered redirect URIs ([`providerConfig.ts`](https://github.com/fells-code/seamless-auth-oidc-provider/blob/v0.1.1/src/providerConfig.ts)). |

The Seamless Auth session itself (its access token, single-use refresh token rotation, and reuse
detection) is not an OAuth grant and is described in
[Security Posture](/understand/security#session-management).
