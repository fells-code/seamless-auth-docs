## Tests That Did Not Run

The tool runs an optional test only when it is selected, and only for the algorithms the server
supports. The API supports EdDSA, ES256, RS256 and RS1
([`webauthnAlgorithms.ts`](https://github.com/fells-code/seamless-auth-api/blob/v0.19.3/src/lib/webauthnAlgorithms.ts)),
so these did not run:

- **Resp-4 P-1, P-2, P-3, P-4, P-6, P-7, P-10, P-11:** the optional algorithms ES256K (secp256k1),
  PS256, PS384, PS512, RS384, RS512, ES384 and ES512, which the API does not offer.
- **Resp-9 P-4,** `tpm` attestation with ES256. The tool lists it as experimental, and it was
  deselected for this run. With it selected, it fails: the attestation is refused with
  `PubArea unique is not same as public key x and y (TPM|ECC)`. The cause is in the WebAuthn
  library the API uses (SimpleWebAuthn 14.0.3): its TPM structure parser does not read the hash
  algorithm that follows an ECDSA signing scheme, so every later field is read two bytes early.
  The authenticator's key matches the credential. A TPM that sets an ECDSA scheme on an ES256 key
  cannot register a passkey with `attestation: 'direct'` until the library is fixed. Reported
  upstream as [SimpleWebAuthn#818](https://github.com/MasterKale/SimpleWebAuthn/issues/818).
- **Resp-9 P-3,** `tpm` attestation whose `pubArea.nameAlg` differs from the algorithm used for
  `attested.name`. The tool did not run it in this configuration.

## Known Deviations

- **Android SafetyNet attestation is not tested.** Tool 1.9.1 has no SafetyNet suite, and
  SafetyNet cannot be tested with fixtures: its statements expire within a minute and the tools
  never emit one. The API still verifies SafetyNet attestation through SimpleWebAuthn.
- **The tools drive a test-only interface.** They speak their own message format, so the API mounts
  `/conformance` routes only when `FIDO_CONFORMANCE_MODE=true`, and never under
  `NODE_ENV=production`
  ([`conformanceMode.ts`](https://github.com/fells-code/seamless-auth-api/blob/v0.19.3/src/config/conformanceMode.ts)).
  Those routes verify registrations and assertions with the same SimpleWebAuthn calls, origins,
  RP ID and supported algorithms as the production WebAuthn routes
  ([`conformance.ts`](https://github.com/fells-code/seamless-auth-api/blob/v0.19.3/src/controllers/conformance.ts),
  [`webauthn.ts`](https://github.com/fells-code/seamless-auth-api/blob/v0.19.3/src/controllers/webauthn.ts)).
  They skip what the tools cannot exercise: the pre-auth flow, session issuance, and the
  deployment's authenticator policy. The options they return echo the selection criteria,
  attestation conveyance and extensions the tools request, as the tools require.
- **Test metadata and roots.** For the run, the API loads the tools' own metadata statements and
  Metadata Service endpoints and trusts the tools' test root certificate, because the tools sign
  every attestation with test keys.

## Earlier Runs

The first runs, on 2026-09-02 against the development branch after v0.7.4, found and fixed two issues: the
conformance metadata loader did not read the tools' nested statement directory, so every
attestation was refused as unlisted, and the registration options carried an extension the tools
had not asked for. The tool's own report was not kept from those runs, so they are not published
as results.
