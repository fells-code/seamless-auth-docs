This page summarizes the current public command surface of `seamless-cli`.

The npm package is named `seamless-cli`. The executable binary is named `seamless`.

---

## Command Summary

| Command                            | Purpose                                                                                    |
| ---------------------------------- | ------------------------------------------------------------------------------------------ |
| `seamless init [project-name]`     | Scaffold a project, either a local self-hosted stack or connected to a managed application |
| `seamless templates list`          | List the starters `init` can scaffold and the flags that select them                       |
| `seamless check`                   | Validate generated project config, Docker, Compose, containers, and local health endpoints |
| `seamless verify [flags]`          | Run the cross-package auth conformance harness (api / adapter / react matrix)               |
| `seamless profile <sub>`           | Manage the instances the CLI targets, and sign in to one with `profile login`              |
| `seamless login [identifier]`      | Sign in to the Seamless portal (managed control plane) with email OTP                      |
| `seamless apps <list\|get>`         | Show the managed applications your portal account owns                                     |
| `seamless whoami`                  | Show the identity, profile, and instance URL behind the current session                    |
| `seamless logout [--all]`          | End the session and clear local tokens                                                     |
| `seamless sessions <sub>`          | List or revoke sessions for the logged-in user                                             |
| `seamless config <sub>`            | Read and write instance system configuration (admin)                                       |
| `seamless users <sub>`             | Admin user management (admin)                                                              |
| `seamless org <sub>`               | Admin organization and membership management (admin)                                       |
| `seamless --help`                  | Print usage                                                                                |
| `seamless --version`               | Print the installed CLI version                                                            |

The `init`, `templates`, `check`, and `verify` commands are for building and testing a stack.
`login` and `apps` use your portal account. The `profile`, `whoami`, `logout`, `sessions`, `config`,
`users`, and `org` commands act as an authenticated client against a running instance (managed or
self-hosted), signed in with `seamless profile login`.

There is no `bootstrap-admin` command. The first admin is the account registered with the owner
email you give `init`. See [Create Your First Admin](/start/firstadmin).

Use `npx seamless-cli ...` when you do not have the package installed globally:

```bash
npx seamless-cli init my-app
npx seamless-cli check
```

## `init`

```bash
seamless init my-app
```

If you omit the project name:

```bash
seamless init
```

The CLI uses the current directory. If the directory is not empty, `init` asks whether to connect it
to a managed application or scaffold in place, because starter files overwrite anything with the
same name. A full integration flow for an existing app is not shipped yet.

### What it does

- prompts for web and backend templates read from the template registry, or takes a template flag
- prompts for an optional mobile app (Expo), or takes `--mobile=expo` to skip the prompt
- prompts for auth mode
- optionally includes the admin dashboard
- generates a working local stack
- writes `seamless.config.json`
- creates `docker-compose.yml`

The mobile app lands in `mobile/` next to the web and API projects, wired to the same API with
`@seamless-auth/react-native`. It is not part of the Docker stack: run it with
`cd mobile && npm install && npx expo start`, which is the command `init` prints. An Android
emulator reaches the API at `http://10.0.2.2:3000`, so set `EXPO_PUBLIC_API_URL` in `mobile/.env`
when you use one. See [React Native SDK](/build/react-native-sdk).

### Current generated stack

The starters come from the [`fells-code/seamless-templates`](https://github.com/fells-code/seamless-templates)
registry at the tag the CLI pins (currently `v0.16.0`). As of that tag the generated path covers:

- React (Vite) or Next.js (full-stack, beta template) for the web app
- Express or Fastify (beta template) for the backend
- an optional Expo (beta) mobile app
- Seamless Auth API in Docker or local source mode
- an admin console served by the API at `/console`, as a separate image or source container, or
  none

### Template flags

```bash
seamless init my-app --oauth
seamless init my-app --web=nextjs
seamless templates list
```

Each template answers to `--<id>`, and some also declare a shorter `--<alias>` (for example
`--oauth` and `--react-oauth` select the same starter). A template flag answers that layer's prompt.
`--web=`, `--api=`, and `--mobile=` take the same ids and aliases and name the layer explicitly. The
flags come from the registry, so `seamless templates list` is the authoritative list.

`--oauth` selects the React OAuth example and then prompts for OAuth providers (Google, GitHub,
Microsoft, GitLab), wires the ones you configure into the auth server, and prints the redirect URI
to register: `http://localhost:5173/oauth/callback`. See
[CLI Init Flow](/operate/cli-init#the---oauth-starter) for the full behavior and the template table.

| Environment variable     | Effect on `init` and `templates list`                                          |
| ------------------------ | ------------------------------------------------------------------------------ |
| `SEAMLESS_TEMPLATES_REF` | Read the published templates repository at this ref instead of the pinned tag   |
| `SEAMLESS_TEMPLATES_DIR` | Read templates from a local checkout instead; takes precedence over the ref     |

### Non-interactive flags

```bash
seamless init my-app --local --yes --email=you@example.com
seamless init my-app --local --yes --email=you@example.com --api=fastify --admin=none
```

Flags answer the questions `init` would otherwise ask, and a question answered by a flag is
skipped. `--yes` answers the rest with the recommended option, so `init` can run in CI, a
Dockerfile, or a script. Valued flags take either `--flag=value` or `--flag value`.

| Flag          | Accepted values                                  | Default                                                          | Effect                                                                                                     |
| ------------- | ------------------------------------------------ | ---------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `--yes`, `-y` | none                                             | off                                                              | Answer every question no flag answers with the recommended option                                          |
| `--local`     | none                                             | off                                                              | Scaffold the self-hosted stack without contacting the control plane                                        |
| `--app`       | a managed application id or infra id             | none                                                             | Connect to that managed application (needs `seamless login`)                                               |
| `--web`       | a web or full-stack template id or alias         | the first selectable web template in the registry (`react-vite`) | Choose the web starter; a full-stack template (`nextjs`) leaves no api layer                               |
| `--api`       | an api template id or alias                      | the first selectable api template in the registry (`express`)    | Choose the backend starter; refused alongside a full-stack web template                                    |
| `--mobile`    | a mobile template id or alias (`expo`, `mobile`) | none                                                             | Add a mobile starter at `mobile/`; `--yes` never adds one on its own                                       |
| `--email`     | an email address                                 | your portal session email, when signed in                        | Owner address, which becomes the admin when you register; required under `--yes` without a portal session  |
| `--auth`      | `docker`, `local`                                | `docker`                                                         | Run the auth server as a Docker image or from local source                                                 |
| `--admin`     | `api`, `image`, `source`, `none`                 | `api`                                                            | Where the admin console is hosted; a full-stack web template accepts only `none`                           |
| `--force`     | none                                             | off                                                              | Under `--yes`, allow scaffolding into a non-empty directory and rotating an existing managed service token |
| `--profile`   | any                                              | none                                                             | Accepted and ignored, with a warning; managed connect uses your portal session                             |

The template defaults are the first selectable entries of each kind in the registry at the pinned
tag. `--web`, `--api`, and `--mobile` take the same ids and aliases as the bare template flags, and
naming one layer twice with different templates is an error. Every flag is validated before a
directory is created.

`--yes` will not make three decisions on its own:

- **Managed or local.** If you are signed in to the portal and have an application to connect,
  pass `--app <id>` or `--local`. If the control plane cannot be reached, `--yes` fails rather than
  falling back to a local stack; pass `--local`.
- **Destructive steps.** Scaffolding into a directory that is not empty and rotating a managed
  application's existing service token both need `--force` as well.
- **OAuth providers.** The `--oauth` starter is scaffolded with no providers configured. Add them
  later with `seamless config oauth-providers add`.

Without a terminal attached and without `--yes`, any question no flag answers fails with an error
that names the flag to pass, instead of waiting for input. See [CLI Init Flow](/operate/cli-init)
for the interactive walkthrough.

### No shortcut

Scaffolding always goes through `init`. A bare project name such as `seamless my-app` is rejected as
an unknown command, and the CLI suggests `seamless init my-app`.

### Managed init

When you are signed in to the portal (`seamless login`) and your account has a provisioned
application, `init` offers to connect the new project to it instead of scaffolding a local auth
server.

- `--app <id>` selects the application and skips the question. It fails rather than falling back to
  local when you are not signed in.
- `--local` forces the self-hosted stack without contacting the control plane.
- `init` issues the application's service token and writes it, the managed auth server URL, and the
  JWKS key id into `api/.env`. Issuing a token invalidates any earlier one, so `init` asks first.
- No local auth server, Docker Compose file, or admin dashboard is generated.

See the [Managed Quickstart](/start/managed-quickstart).

## `check`

```bash
seamless check
```

Use this when you want to validate a generated project.

It checks:

- `seamless.config.json`
- configured web and API paths
- Docker availability
- `docker-compose.yml`
- expected running containers
- API health at `http://localhost:3000/`
- auth health at `http://localhost:5312/health/status`
- admin availability at `http://localhost:5174`

It does not currently check Terraform, AWS CLI, or deployment state.

## `verify`

```bash
seamless verify
```

Runs a cross-package auth conformance harness. It stands up the ecosystem with Docker Compose
(Postgres, the auth API, an Express adapter app and a Fastify adapter app, and the React starter),
then runs a Playwright matrix across the api, adapter, and react layers and prints a flow x layer
pass/fail grid alongside JUnit and HTML reports.

- **api** verifies the auth API directly (Bearer / JSON).
- **adapter** verifies the cookie path through both adopter frameworks, with the same specs run
  twice: once against `@seamless-auth/express` and once against `@seamless-auth/fastify`. Each
  framework gets its own row in the grid, so a regression in one shows up on its own.
- **react** drives the React starter in a real browser (Chromium), including passkeys via a virtual
  authenticator and OAuth via an in-process mock OIDC provider.

Covered flows include register, email and phone OTP, magic-link, passkey register and login, OAuth,
TOTP, step-up, refresh, sessions, logout, organizations, the owner admin grant, and JWKS.

### Modes and flags

```bash
seamless verify              # test the published @seamless-auth/* packages
seamless verify --local      # build the SDKs from local source (pre-publish contract test)
```

| Flag              | Effect                                                                                                                              |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `--local`         | Build `@seamless-auth/*` (core, express, fastify, and react when the browser layer runs) from local source instead of published     |
| `--api-only`      | Run only the api project (skip both adapters and react)                                                                             |
| `--no-react`      | Skip the browser layer                                                                                                              |
| `--filter=<flow>` | Run only tests matching `<flow>` (passed to Playwright as `--grep`), in every layer. The space form `--filter <flow>` is not parsed |
| `--keep-up`       | Leave the Docker stack running after the run                                                                                        |

Without `--filter`, each web template runs only the flows its `template.json` lists under
`verify.flows`, or every flow when it lists none. `--filter` replaces that per-template scope.

| Adapter | Package under test       | Compose service   | URL the harness calls                                    |
| ------- | ------------------------ | ----------------- | -------------------------------------------------------- |
| Express | `@seamless-auth/express` | `adapter`         | `http://localhost:3000` (`SEAMLESS_ADAPTER_URL`)         |
| Fastify | `@seamless-auth/fastify` | `adapter-fastify` | `http://localhost:3001` (`SEAMLESS_FASTIFY_ADAPTER_URL`) |

`verify` sets both URLs for the harness itself, so they are listed to explain the grid, not as
settings. Without `--local`, each adapter app installs the version its `package.json` pins, and the
end-of-run summary lists the package versions that were tested.

Requires Docker. The sibling repos are resolved relative to the CLI checkout and can be overridden:

| Environment variable     | Overrides                                                                                       |
| ------------------------ | ----------------------------------------------------------------------------------------------- |
| `SEAMLESS_API_DIR`       | The `seamless-auth-api` checkout the auth server is built from                                  |
| `SEAMLESS_SERVER_DIR`    | The `seamless-auth-server` checkout (needed for `--local`)                                      |
| `SEAMLESS_REACT_SDK_DIR` | The `seamless-auth-react` checkout (needed for `--local` browser runs)                          |
| `SEAMLESS_TEMPLATES_DIR` | The `seamless-templates` checkout; every runnable web template in its `registry.json` is driven |
| `SEAMLESS_REACT_DIR`     | A single template directory to drive instead of the whole registry                              |

`SEAMLESS_VERIFY_COMPOSE_OVERRIDE` names an extra Compose file that `verify` layers over its base
`verify/docker-compose.verify.yml`, passed as a second `-f` on every `docker compose` call it makes
(build, up, logs, and teardown). It is unset by default, and a local run needs nothing from it. CI
points it at `verify/docker-compose.cache.yml`, which attaches a GitHub Actions build cache to each
image. A relative path resolves from the CLI's `verify/` directory, so an absolute path is safer.

`verify` always reads templates from a local checkout, so `SEAMLESS_TEMPLATES_REF` (which selects a
ref of the published repository for `init`) has no effect here. A reusable GitHub workflow runs
`seamless verify --local` on ecosystem PRs so a change in one repo is tested against the others.

## `profile`

Profiles are named pointers to the Seamless Auth instances the CLI targets. They are stored in
`~/.config/seamless/config.json` (respects `XDG_CONFIG_HOME`). The file holds only non-secret instance
and identity metadata, never tokens.

```bash
seamless profile list
seamless profile add <name> --instance-url <url> [--identifier-type email|phone]
seamless profile use <name>
seamless profile remove <name>
seamless profile login [name] [identifier] [--identifier <email>] [--local]
```

- `list` shows configured profiles; the active one is marked with `*`.
- `add` creates or updates a profile and prompts interactively if flags are omitted. Non-local URLs
  must be `https`.
- `use` sets the active profile for later commands.
- `remove` deletes a profile and clears its keychain tokens.
- `login` signs in to that instance so `users`, `config`, `org`, and `sessions` can run. It defaults
  to the active profile and does not change which profile is active.

Choose the active profile per command with `--profile <name>` or the `SEAMLESS_PROFILE` environment
variable.

## `login`

```bash
seamless login [identifier] [--identifier <email>] [--local]
```

Signs in to the Seamless portal, the managed control plane. This is the account that authorizes
listing managed applications and connecting a project to one, and it needs no profile. Prompts for
the identifier (or pass it positionally or with `--identifier`) and the emailed code, then stores the
session in the OS keychain (macOS Keychain, Windows Credential Manager, or Linux Secret Service).

To sign in to an auth instance you administer, use `seamless profile login` instead. The two are
separate accounts even when they share an email address.

## `apps`

```bash
seamless apps list [--json]
seamless apps get <id|name|infra-id> [--json]
```

Shows the managed applications your portal account owns. Requires `seamless login`, not an instance
profile. `apps get` reports whether a service token has been issued, masked, never the live value.

---

## `whoami`

```bash
seamless whoami [--profile <name>]
```

Shows the identity behind the active session (`sub`, email, roles), along with the profile name and
instance URL. Fails cleanly if you are not logged in.

---

## `logout`

```bash
seamless logout [--all] [--profile <name>]
```

Ends the current session on the instance and clears the local keychain tokens. `--all` revokes every
session for the user before clearing local tokens.

---

## `sessions`

```bash
seamless sessions list
seamless sessions revoke <id>
seamless sessions revoke --all
```

Lists active sessions for the logged-in user (session id, device or user agent, IP, and last-used
time, with the current session marked) and revokes them. Revoking the current session or `--all`
prompts for confirmation and then clears local tokens.

## `config`

Read and write the instance system configuration. Requires an admin role on the target instance.

```bash
seamless config get [key] [--json]
seamless config set <key> <value>
seamless config roles [--json]
seamless config diff <file>
seamless config apply <file> [--dry-run]
```

`set` parses the value as JSON, falling back to a string (for example
`seamless config set login_methods '["email_otp","passkey"]'`). `apply` writes a local JSON config
file after a confirmation prompt.

---

## `users`

Admin user management. Requires an admin role.

```bash
seamless users list [--limit <n>] [--offset <n>] [--json]
seamless users delete <id>
seamless users credentials <id> [--json]
seamless users prepare-device-replacement <id> [--keep-sessions] [--keep-passkeys] [--keep-totp]
```

`prepare-device-replacement` is admin-assisted account recovery and needs an elevated (stepped-up)
session.

---

## `org`

Admin organization and membership management. Requires an admin role.

```bash
seamless org list [--json]
seamless org create <name> [--slug <slug>]
seamless org get <id> [--json]
seamless org update <id> [--name <name>] [--slug <slug>]
seamless org members list <orgId> [--json]
seamless org members add <orgId> (--user <id> | --email <email>) [--roles a,b] [--scopes a,b]
seamless org members update <orgId> <userId> [--roles a,b] [--scopes a,b]
seamless org members remove <orgId> <userId>
```

## Removed Or Not Currently Shipped

The current `../seamless-cli` source does not include these commands:

- `seamless deploy`
- `seamless destroy`
- `seamless contribute`
- `seamless bootstrap-admin` (replaced by the owner email asked for during `init`)
