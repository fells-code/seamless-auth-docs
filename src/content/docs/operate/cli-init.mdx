This guide explains exactly what happens when you run:

```bash
npx seamless-cli init my-app
```

Scaffolding always goes through `init`; a bare project name is rejected as an unknown command.
Running the CLI with no command prints help.

This guide focuses on local project generation, auth wiring, Docker setup, and admin dashboard
inclusion.

---

## Mental Model

```
init → prompts → generators → config → ready-to-run app
```

---

## Step 0: Directory Setup

If you pass a project name:

```bash
npx seamless-cli init my-app
```

The CLI will:

- Create a new folder
- Ensure it does not already exist
- Use it as the project root

If you run `npx seamless-cli init` with no project name, it uses the current directory. If that
directory is not empty, `init` asks what to do, because starter files overwrite anything with the
same name: scaffold in place, or (when you are signed in to the portal) connect the existing project
to a managed application. Under `--yes` it refuses unless you also pass `--force`. A full integration
flow for an existing self-hosted app is still future work.

---

## Step 1: Interactive Prompts

The CLI asks a series of questions to shape your stack.

### Web Framework

- React (Vite), basic example
- React (Vite), OAuth example

A Next.js App Router starter exists in `seamless-templates` (`templates/fullstack/nextjs`), but
`seamless init` does not offer it yet: it is a full-stack template that serves `/auth` itself, which
the CLI does not support yet. Copy that directory and follow its README, or see
[Next.js](/build/nextjs).

This determines your frontend scaffold.

---

### Backend Framework

- Express
- Fastify (beta)

This determines your API server.

---

### Mobile App

- None (the default)
- Expo (React Native)

Optional. Picking Expo adds a `mobile/` project on `@seamless-auth/react-native`, signing in
against the same API over bearer transport. Pass `--mobile=expo` to answer without the prompt.

---

### Auth Mode

- Docker (recommended)
- Local dev server (advanced)

**Docker mode**:

- Runs full auth stack in containers
- Closest to production

**Local mode**:

- Generates the auth server source into `./auth`
- Still relies on Docker for the full local stack
- Prompts about Docker, but the current source enables Docker either way because it is required for
  the full generated stack

---

### Admin Dashboard

You choose whether to include the Admin UI.

If enabled:

#### Admin Source

- Docker image (recommended)
- Source (for customization)

---

## Step 2: Generators Run

Based on your answers, the CLI executes generators.

### Frontend

```ts
await generateReactStarter({ root })
```

Creates:

- React app (Vite)
- Auth-aware starter frontend

---

### Backend

```ts
await generateExpressStarter({ root })
```

Creates:

- Express API
- Auth-ready endpoints

---

### Auth Server

If using local mode:

```ts
await generateAuthServer({ root }, 'local')
```

This generates the Seamless Auth server locally.

---

### Docker Setup

```ts
await generateDockerCompose(root, {
  authMode,
  adminMode,
  includeAdmin,
})
```

Creates:

- Postgres container
- Auth server container
- Admin UI container (optional)

---

## Step 3: Environment Configuration

The CLI wires environment variables automatically.

### API

```ts
configureApiEnv(root, sharedConfig)
```

### Web

```ts
configureWebEnv(root)
```

### Auth

```ts
configureAuthLocalEnv(root)
```

This ensures:

- Services can communicate
- URLs and ports are aligned

---

## Step 4: Project Config File

```ts
generateSeamlessConfig(root, { ... })
```

Creates:

```txt
seamless.config.json
```

This file stores:

- Framework choices
- Auth mode
- Admin configuration

---

## Step 5: Final Output

The CLI prints next steps. In the Docker-backed path, those are:

1. `docker compose up`
2. register in the browser with the owner email you gave `init`, which makes that account an admin

It also prints the expected local service URLs for auth, API, web, and admin.

## Generated Project Structure

```txt
my-app/
  web/
  api/
  auth/                  # local auth mode only
  admin/                 # admin source mode only
  docker-compose.yml
  seamless.config.json
  README.md
```

## What Gets Wired Automatically

- Auth endpoints
- Session handling
- Secure cookies
- Frontend SDK integration
- Backend auth validation

---

## Key Design Decisions

### Opinionated Defaults

The CLI chooses:

- Secure session handling
- Passwordless flows
- Best-practice structure

---

### Full-Stack by Default

You always get:

- `web/` frontend starter
- `api/` backend starter
- local Docker Compose wiring
- `seamless.config.json`
- auth server runtime wiring

You may also get:

- `auth/` source when local auth mode is selected
- `admin/` source when admin source mode is selected

---

### Docker-First

Even in local mode, Docker is used to ensure consistency.

---

## Common Pitfalls

- Running in a non-empty directory
- Skipping Docker setup
- Misunderstanding auth mode differences
