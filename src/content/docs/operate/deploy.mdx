There are two ways to run Seamless Auth in production. The managed offering hosts the auth instance
for you. Self-hosting means you provision and operate the stack yourself.

---

## Managed hosting

On the managed path, Seamless runs the auth instance for you. You create an application in the portal
at [https://dashboard.seamlessauth.com](https://dashboard.seamlessauth.com), pick a plan, and Seamless
provisions a dedicated hosted instance. Its Auth Server URL is
`https://<infra-id>.trials.seamlessauth.com` on the Trial plan and
`https://<infra-id>.seamlessauth.com` on paid plans; copy the exact value from **Credentials** →
**Auth API Configuration**. You point the backend adapter at that URL with a portal-issued service
token.

On this path you do not provision Postgres, manage signing keys, or run the auth server. See the
[Managed Quickstart](/start/managed-quickstart).

---

## Self-hosting

The [Production Checklist](/operate/production-checklist) is the step-by-step guide for taking a
self-hosted install to a public host. Start there.

The CLI ([`seamless-cli`](https://github.com/fells-code/seamless-cli)) scaffolds and inspects
projects; it does not deploy them. It has no `deploy` or `destroy` command, so provisioning and
operating the servers is up to you. See the [CLI command reference](/reference/cli-commands) for
what it does ship.

<Aside type="note">
  `seamless init` decides between a managed and a self-hosted project. `--local` always scaffolds
  the self-hosted stack. Without it, a session from `seamless login` with a managed application
  lets `init` connect that application instead; with `--yes` it will not guess, so pass `--app <id>`
  or `--local`. When you are not logged in, `init` scaffolds a local project and says so.
</Aside>

### What the CLI prepares

`seamless init --local` generates a local project with:

- a web starter and a backend starter (or a full-stack starter)
- the Seamless Auth API in Docker or local-source mode
- the admin dashboard, served by your backend at `/console`, as a separate container, or not at all
- Docker Compose wiring
- local secrets and service URLs
- `seamless.config.json`

That is a working local stack in development mode, not a production configuration. Its compose file
returns sign-in codes in responses and signs tokens with a key generated on disk, so do not deploy
it as it is. The [Production Checklist](/operate/production-checklist) says what to change.

### What self-hosted operators own

If you self-host, you own:

- hosting the auth API, your application backend, your web app, and the admin console if you use it
- provisioning Postgres
- setting stable production secrets
- configuring JWKS signing keys
- configuring HTTPS, CORS, origins, cookie domain, and proxy headers
- managing OAuth provider callback URLs and provider secrets
- monitoring, logging, alerting, backup, and restore testing
- upgrades and rollback

Use [Environment Variables](/reference/environment-variables),
[System Config Reference](/reference/system-config), and
[Cookie, Session, And Token Reference](/reference/cookies-sessions-tokens) alongside the checklist.

The managed offering handles these for you.
