# Running In Production

There are two ways to run Seamless Auth in production. The managed offering hosts the auth instance
for you. Self-hosting means you provision and operate the stack yourself.

This page previously documented an AWS dev-tier `deploy` and `destroy` command flow. That flow is not
in the current `../seamless-cli` source, so it is no longer described here as shipped.

---

## Managed hosting

On the managed path, Seamless runs the auth instance for you. You create an application in the portal
at [https://dashboard.seamlessauth.com](https://dashboard.seamlessauth.com), pick a plan, and Seamless
provisions a dedicated hosted instance at `https://<your-app-id>.seamlessauth.com`. You point the SDKs
at that URL and a portal-issued service token.

On this path you do not provision Postgres, manage signing keys, or run the auth server. See the
[Managed Quickstart](/start/managed-quickstart).

---

## Self-hosted CLI surface today

For self-hosting, the public CLI command surface is:

```bash
seamless init [project-name]
seamless check
seamless bootstrap-admin [email]
seamless verify
seamless login
seamless profile <list|add|use|remove>
seamless --help
seamless --version
```

The CLI also exposes `whoami`, `logout`, `sessions`, and the admin commands `config`, `users`, and
`org` against a configured instance. See the [CLI command reference](/reference/cli-commands) for the
full surface.

There is no `seamless deploy` or `seamless destroy` implementation in `../seamless-cli`.

<Aside type="note">
  A managed `init` flow, where `seamless init` connects a scaffolded app to your hosted managed
  instance instead of hardwiring localhost, is planned but not shipped. It is tracked as
  `fells-code/seamless-cli#59`. Today `seamless init` only scaffolds a self-hosted local stack pointed
  at localhost.
</Aside>

## What the CLI can prepare today

`seamless-cli` can generate a local self-hosted project with:

- React web starter
- Express API starter
- Seamless Auth API in Docker or local-source mode
- optional admin dashboard in Docker image or source mode
- Docker Compose wiring
- local secrets and service URLs
- `seamless.config.json`

That gives you a production-shaped local stack, but it is not a hosted deployment workflow.

---

## What self-hosted operators still own

If you self-host, until deployment automation ships you own:

- hosting the auth API, application API, web app, and optional admin dashboard
- provisioning Postgres
- setting stable production secrets
- configuring JWKS signing keys
- configuring HTTPS, CORS, origins, cookie domain, and proxy headers
- managing OAuth provider callback URLs and provider secrets
- monitoring, logging, alerting, backup, and restore testing

Use [Environment Variables](/reference/environment-variables),
[System Config Reference](/reference/system-config), and
[Cookie, Session, And Token Reference](/reference/cookies-sessions-tokens) when planning those
deployment surfaces.

The managed offering handles these for you.

---

## Documentation Rule

When documenting deployment work:

- do not describe `deploy` or `destroy` as shipped unless those commands exist in `../seamless-cli`
- do not describe managed `init` as shipped until `seamless-cli#59` lands
- label future deployment flows as planned or in progress
- tie infrastructure claims to current source code or generated files
- keep operator-owned production hardening separate from CLI-generated local setup
