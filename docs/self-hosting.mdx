# Self Hosting

Seamless Auth is designed to run as part of your infrastructure. In production, the recommended approach is to run the auth server as a container using the official image.

This guide focuses on how to deploy Seamless Auth in a way that is predictable, secure, and easy to operate.

---

## Recommended Approach

Use the official container image:

```bash
docker pull ghcr.io/fells-code/seamless-auth-api:latest
```

Run the auth server alongside your API and database using containers.

This provides:

* consistent runtime behavior
* isolated services
* reproducible deployments

The same model used in development with Docker Compose should carry into production.

---

## Minimal Production Setup

A typical deployment includes:

* Auth server (container)
* API server (container)
* Database (managed or containerized)
* Web application (static host or container)

All services communicate over a private network.

---

## Running the Auth Server

The auth server should be deployed using the official image.

Example:

```yaml
services:
  auth:
    image: ghcr.io/fells-code/seamless-auth-api:latest
    environment:
      NODE_ENV: production
      PORT: 5312
      ISSUER: https://auth.yourdomain.com
```

Do not run the development Dockerfile in production.

---

## Environment Variables

All configuration is provided through environment variables.

Production requires:

* Cookie signing key
* API service token
* JWKS configuration
* Allowed origins
* Database connection settings

Secrets should be injected at runtime using your platform’s secret management system.

Do not commit production secrets to source control.

---

## HTTPS and Domains

All production traffic should use HTTPS.

Recommendations:

* Terminate TLS at a load balancer or reverse proxy
* Use a dedicated domain for the auth server
* Set cookie `Secure` and appropriate `SameSite` values

Example:

```
https://auth.yourdomain.com
```

The API and web application should use this endpoint for authentication.

---

## Networking

Services should communicate over an internal network.

* API → Auth via internal hostname
* Auth → Database via internal hostname

The browser should only interact with:

* your web application
* your API

The auth server should not be exposed unnecessarily.

---

## Scaling

The auth server is stateless.

To scale:

* run multiple auth containers
* use a shared database
* place a load balancer in front

Session validation relies on signed tokens and database state, so no session affinity is required.

---

## Database

The database stores:

* users
* credentials
* sessions

Use a managed database when possible.

Ensure:

* backups are enabled
* access is restricted
* connections are encrypted

---

## Deployment Platforms

Seamless Auth works with:

* Docker Compose (small deployments)
* ECS or Kubernetes (scaled environments)
* Virtual machines
* Platform-as-a-Service

The system does not depend on any specific provider.

---

## Upgrades

When upgrading:

* pull the latest image
* review release notes
* test in staging
* deploy gradually

Database migrations should be applied before or during deployment.

---

## Responsibility

When self-hosting, you are responsible for:

* infrastructure security
* secret management
* monitoring and logging
* backups and recovery

Seamless Auth provides the authentication system. You control how it is run.

---

## Summary

The recommended production model is:

* run the auth server as a container
* use the official image
* manage configuration through environment variables
* keep all communication inside your infrastructure

This keeps authentication predictable and under your control.
