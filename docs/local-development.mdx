# Local Development

At this point you should have a running Seamless Auth stack.

This section focuses on what was generated and how to work with it during development.

The goal is to make the system understandable, not just runnable.

---

## What You Have

A typical project created with `create-seamless` looks like this:

```text
/web   → React application
/api   → Express API
/auth  → Seamless Auth server
```

Each piece has a specific role:

- The web app handles user interaction and authentication UI
- The API validates sessions and enforces authorization
- The auth server manages identity, credentials, and session state

You are working with a complete system, not a library.

---

## The Web Application

The web starter is a React application that already includes Seamless Auth integration.

### AuthProvider

At the root of the app, the `AuthProvider` is configured:

```tsx
<AuthProvider apiHost={import.meta.env.VITE_API_URL}>
  <App />
</AuthProvider>
```

This connects the frontend to your API and establishes the session context.

---

### useAuth Hook

Authentication state is accessed through the `useAuth` hook:

```tsx
const { user, login, register, logout } = useAuth()
```

This gives you:

- `user` → current authenticated user
- `login()` → start authentication
- `register()` → create a new credential
- `logout()` → clear session

No tokens are handled directly in the frontend.

---

### Authenticated UI

The starter includes basic examples of:

- registration
- login
- conditional rendering based on `user`

You can build on this pattern to protect routes or show user-specific content.

---

## The API Server

The API starter is where authentication is enforced.

This is where requests are trusted and authorization decisions are made.

---

### createSeamlessServer

The server is initialized using:

```ts
createSeamlessServer({
  authServerUrl: process.env.AUTH_SERVER_URL,
  cookieSecret: process.env.COOKIE_SIGNING_KEY,
  serviceSecret: process.env.API_SERVICE_TOKEN,
  issuer: process.env.APP_ORIGIN,
  audience: process.env.AUTH_SERVER_URL,
  jwksKid: process.env.JWKS_KID,
})
```

This connects your API to the auth server and enables session validation.

---

### requireAuth

To protect a route:

```ts
app.get('/protected', requireAuth, (req, res) => {
  res.json({ user: req.user })
})
```

If the request does not have a valid session, it is rejected.

---

### requireRole

For role-based access:

```ts
app.get('/admin', requireRole('admin'), (req, res) => {
  res.send('admin only')
})
```

Authorization is explicit and handled in your code.

---

### Request Lifecycle

For a protected request:

1. Browser sends cookies with the request
2. Middleware validates the session
3. `req.user` is populated
4. Your handler runs with a trusted user

There is no client-side token validation.

---

## The Auth Server

The auth server is responsible for:

- registering credentials
- verifying authentication challenges
- issuing session cookies
- signing and exposing JWKS

You do not interact with it directly from your application code.

Your API communicates with it through defined endpoints and shared configuration.

---

## Working Locally

When developing:

- The web app talks to the API on `localhost`
- The API validates sessions against the auth server
- The auth server reads and writes session state to the database

All communication happens over HTTP using cookies.

This mirrors production behavior.

---

## Making Changes

You can modify each layer independently:

- Update UI in `/web`
- Add routes in `/api`
- Extend identity logic in `/auth`

Changes are picked up immediately when running in development mode.

---

## Debugging

When something does not work as expected:

- Check API logs for authentication errors
- Check auth server logs for verification issues
- Inspect cookies in the browser
- Confirm environment variables match across services

Most issues come from mismatched configuration between services.
