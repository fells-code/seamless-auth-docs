# API Integration

This guide explains how Seamless Auth integrates into your API and what surfaces are exposed to you as a developer.

The system is designed so that authentication is handled once, at the edge of your API, and everything downstream operates on trusted user context.

---

## Integration Model

Seamless Auth separates concerns into two layers:

- The core package handles verification and identity
- The adapter connects that logic to your framework

Your API is responsible for:

- enforcing authentication
- enforcing authorization
- handling business logic

---

## Express Integration Overview

The Express adapter provides a small set of primitives:

- `createSeamlessServer`
- `requireAuth`
- `requireRole`
- `optionalAuth` (if used)

These are enough to fully integrate authentication into your API.

---

## createSeamlessServer

This initializes the connection between your API and the auth server.

```ts
import { createSeamlessServer } from '@seamless-auth/express'

createSeamlessServer({
  authServerUrl: process.env.AUTH_SERVER_URL,
  cookieSecret: process.env.COOKIE_SIGNING_KEY,
  serviceSecret: process.env.API_SERVICE_TOKEN,
  issuer: process.env.APP_ORIGIN,
  audience: process.env.AUTH_SERVER_URL,
  jwksKid: process.env.JWKS_KID,
})
```

This configuration enables:

- cookie verification
- token signature validation
- server-to-server communication with the auth server

It should be called once during application startup.

---

## requireAuth

This middleware enforces authentication.

```ts
import { requireAuth } from '@seamless-auth/express'

app.get('/api/me', requireAuth(), (req, res) => {
  res.json({ user: req.user })
})
```

Behavior:

- reads cookies from the request
- verifies the session
- resolves the user
- attaches `req.user`

If verification fails, the request is rejected with `401 Unauthorized`.

---

## optionalAuth

In some cases, you may want authentication to be optional.

```ts
import { optionalAuth } from '@seamless-auth/express'

app.get('/api/public', optionalAuth(), (req, res) => {
  if (req.user) {
    return res.json({ message: 'authenticated', user: req.user })
  }

  res.json({ message: 'anonymous' })
})
```

This allows a route to behave differently based on authentication state without rejecting unauthenticated requests.

---

## requireRole

Authorization is enforced using roles.

```ts
import { requireRole } from '@seamless-auth/express'

app.get('/api/admin', requireAuth(), requireRole('admin'), (req, res) => {
  res.json({ ok: true })
})
```

Behavior:

- checks roles on `req.user`
- rejects with `403 Forbidden` if missing

Authorization logic remains explicit in your routes.

---

## Request Context

After `requireAuth` runs, your request includes a normalized user object.

Typical shape:

```ts
req.user = {
  sub: string,
  email?: string,
  roles: string[],
}
```

This object is safe to trust and use throughout your API.

---

## How Verification Works

For each request:

1. Cookies are read from the request
2. The session token is extracted
3. The token is verified using the signing key or JWKS
4. The user is resolved from the token payload
5. The result is attached to `req.user`

No external network calls are required during validation.

---

## Server-to-Server Communication

The API uses a service token to communicate with the auth server.

This enables:

- session validation
- identity resolution
- internal operations

The service token is shared between services and should remain private.

---

## Mapping Users to Your Domain

Most applications maintain their own user records.

A common pattern:

```ts
app.use(async (req, res, next) => {
  if (!req.user) return res.status(401).end()

  let user = await User.findByPk(req.user.sub)

  if (!user) {
    user = await User.create({
      id: req.user.sub,
      email: req.user.email,
    })
  }

  req.appUser = user
  next()
})
```

This keeps authentication separate from application data.

---

## Error Handling

Errors are consistent across the system:

- Invalid or missing session → `401 Unauthorized`
- Missing role → `403 Forbidden`

Clients can rely on these responses without custom parsing.

---

## Adapter Model

Adapters exist only to connect the core to your framework.

The authentication model does not change when switching frameworks.

Future adapters will follow the same pattern:

- extract request data
- call core verification
- attach user context
