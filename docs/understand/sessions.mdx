# Sessions

Sessions are one of the core security primitives in Seamless Auth.

Unlike purely stateless browser tokens, Seamless Auth sessions are explicit records with lifecycle,
device context, and revocation state.

---

## Mental Model

```txt
User -> verifies -> Session created -> Cookie issued -> Requests authenticated
```

---

## What A Session Represents

A session represents a logged-in browser, device, or server-side auth context.

Each session:

- belongs to one user
- has its own expiration lifecycle
- carries request/device context
- can be revoked independently

---

## Important Session Fields

| Field              | Description                    |
| ------------------ | ------------------------------ |
| `id`               | Unique session ID              |
| `userId`           | Owning user                    |
| `mode`             | `web` or `server`              |
| `refreshTokenHash` | Stored refresh token reference |
| `lastUsedAt`       | Most recent activity           |
| `expiresAt`        | Absolute expiration            |
| `idleExpiresAt`    | Idle timeout cutoff            |
| `deviceName`       | Friendly device label          |
| `userAgent`        | Device/browser info            |
| `ipAddress`        | Request origin                 |
| `revokedAt`        | Revocation timestamp           |
| `revokedReason`    | Revocation reason              |

---

## Expiration Model

Seamless Auth uses two main expiration concepts.

### Absolute expiration

`expiresAt` is the hard stop for the session.

### Idle expiration

`idleExpiresAt` limits abandoned sessions and is based on activity.

---

## Lifecycle

```txt
Created -> Active -> Idle -> Expired
                 \
                  -> Revoked
```

---

## How Sessions Are Created

1. the user completes a passwordless verification flow
2. the auth server creates a session record
3. a secure cookie is issued
4. backend and frontend integrations recognize the authenticated state

---

## Why Sessions Are First-Class

This design enables:

- device-level visibility
- per-session revocation
- multi-device support
- explicit server-side lifecycle tracking
- better operator workflows in the admin dashboard

---

## Revocation

Sessions can be revoked:

- from the current-user session APIs
- from admin routes
- during lifecycle or security handling

When revoked:

- the session can no longer be used
- `revokedAt` is set
- a `revokedReason` may also be recorded

---

## Multi-Device Example

A user signs in from:

- a laptop
- a phone
- a work browser

That results in separate sessions. Revoking one does not require revoking the others.
