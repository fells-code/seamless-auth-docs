# Users & Roles

Users represent identities in SeamlessAuth and carry the role data your application uses for
authorization.

---

## Mental Model

```txt
User -> has roles -> determines access
```

---

## Important User Fields

| Field           | Description                        |
| --------------- | ---------------------------------- |
| `id`            | Unique user ID                     |
| `email`         | Unique email                       |
| `phone`         | Unique phone                       |
| `roles`         | Array of assigned roles            |
| `revoked`       | Whether authentication is disabled |
| `emailVerified` | Email verification status          |
| `phoneVerified` | Phone verification status          |
| `verified`      | Fully verified status              |
| `challenge`     | In-progress auth challenge         |
| `lastLogin`     | Last successful login              |

---

## Roles

Roles are stored directly on the user record.

Example:

```txt
["user", "admin", "betaUser"]
```

That makes role checks explicit and easy to reason about in both frontend and backend code.

---

## System Role Configuration

Role behavior is shaped by system configuration values such as:

- `default_roles`
- `available_roles`

Those values control:

- which roles new users receive by default
- which roles are valid in the system

---

## Authorization Model

SeamlessAuth gives you identity and role data. Your application still decides how to enforce access.

That can look like:

- UI checks with `hasRole('admin')`
- backend middleware such as `requireRole('admin')`
- product-specific role combinations in your own application code

Example:

```tsx
if (hasRole('admin')) {
  return <AdminPanel />
}
```

---

## Verification State

Users move through a verification lifecycle:

```txt
Unverified -> Email verified -> Phone verified -> Fully verified
```

The exact path depends on the auth flow your app is using.

---

## Revoked Users

If a user is revoked:

- they should no longer be able to authenticate
- existing sessions should be treated as invalidated

Revocation is how the system distinguishes a real user record from one that is still allowed to
participate in auth flows.

---

## Admin Users

Admins are normal users with an `admin` role.

That simplicity matters because it keeps authorization explicit across:

- admin dashboard access
- backend route protection
- operator actions
