# Authentication Flow

This page explains how authentication works end to end in Seamless Auth.

The goal is to make the flow explicit so you can reason about security, debug issues locally, and extend the system with confidence.

Seamless Auth uses passwordless verification to establish a session, then relies on secure cookies and server-side validation for all subsequent requests.

---

## High-Level Overview

Authentication happens in two phases:

1. Verification — prove control of an identity
2. Session — establish a trusted session using cookies

Once a session is established, the system relies on that session for all future requests.

---

## Step-by-Step Flow

### 1. Initiate Authentication

The flow begins in the web application.

A user initiates authentication using the Seamless Auth SDK.

Common triggers:

- Entering an email or phone number for OTP
- Starting a WebAuthn or passkey challenge

The web application sends a request to the auth server to begin verification.

---

### 2. Verification

The auth server performs verification.

Examples include:

- Generating and validating a one-time password
- Handling a WebAuthn challenge and response

In development, OTPs may be logged to the console. In production, delivery is handled by external providers.

Verification always happens on the auth server. The frontend does not validate credentials.

---

### 3. Session Issuance

After successful verification, the auth server issues a session.

This includes:

- A short-lived access cookie
- A refresh cookie if enabled

Key properties:

- Cookies are HTTP-only
- Cookies are same-site by default
- Tokens are signed and verifiable
- Cookies are set in the auth server response

The browser stores these cookies automatically.

---

## What the Browser Stores

After authentication, the browser stores only HTTP-only cookies.

It does not store:

- Passwords
- Access tokens in JavaScript
- Identity provider secrets

This reduces exposure to client-side attacks.

---

## Authenticated Requests

Once a session exists, the flow is straightforward.

### Web → API

1. The web application makes a request to your API
2. The browser includes cookies automatically
3. The API validates the session using middleware
4. The request proceeds with authenticated user context

The frontend does not manually attach tokens.

---

## API Session Validation

Authentication is enforced in the API.

A typical request lifecycle:

1. `requireAuth` validates the access cookie
2. The session token is verified using the signing key or JWKS
3. A normalized user object is attached to the request
4. Handlers access `req.user`

If validation fails, the request is rejected with a 401 response.

---

## Authorization

Authentication establishes identity. Authorization controls access.

After `requireAuth`, authorization is handled explicitly.

Example:

```ts
app.get(
  '/api/beta_users',
  requireAuth({ cookieSecret: process.env.COOKIE_SIGNING_KEY! }),
  requireRole('betaUser'),
  handler,
)
```

Authorization rules are defined in application code.

---

## Session Expiration and Renewal

Sessions are time-bound.

- Access cookies expire after a short duration
- Refresh logic may issue new access cookies
- Expired sessions require re-authentication

From the application’s perspective, an expired session is treated as unauthenticated.

---

## Local Development Behavior

In local development:

- OTP values may be logged to the console
- Cookies are issued on localhost
- No external providers are required

The session model and validation flow remain the same as production.

---

## Why This Model

This approach provides:

- No tokens exposed to JavaScript
- No redirect-based flows
- Clear trust boundaries
- Explicit enforcement in the API
- Consistent behavior across environments

Authentication becomes part of your system rather than an external dependency.
