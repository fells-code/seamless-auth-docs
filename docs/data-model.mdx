# Data Model

This section explains how Seamless Auth stores identity, credentials, and sessions.

The data model is designed to keep authentication explicit and inspectable. Each table represents a specific part of the authentication system. Nothing is hidden behind external services.

---

## Overview

At a high level, the system is built around five core concepts:

- Users
- Credentials
- Sessions
- Events
- Configuration

These map directly to database tables and are used across the auth server and API.

---

## Users

The `users` table represents identity.

```sql
users
```

Key fields:

- `id` → primary identifier
- `email` and `phone` → unique identity attributes
- `roles` → authorization data
- `verified`, `email_verified`, `phone_verified` → verification state
- `revoked` → whether the account is disabled

Users do not store passwords. Authentication is based on verification methods such as passkeys or magic links.

---

## Credentials

The `credentials` table stores WebAuthn credentials.

```sql
credentials
```

Key fields:

- `id` → credential identifier
- `userId` → associated user
- `publicKey` → cryptographic public key
- `counter` → replay protection
- `transports`, `deviceType`, `browser` → device metadata

Each credential represents a device or authenticator registered by the user.

---

## Sessions

The `sessions` table tracks active and historical sessions.

```sql
sessions
```

Key fields:

- `id` → session identifier
- `userId` → associated user
- `refreshTokenHash` → hashed refresh token
- `expiresAt` and `idleExpiresAt` → session lifetime
- `revokedAt`, `revokedReason` → revocation tracking

Sessions are issued after successful authentication and are validated on every request.

---

## Auth Events

The `auth_events` table records authentication activity.

```sql
auth_events
```

Key fields:

- `user_id` → associated user
- `type` → event type (login, logout, verification)
- `ip_address`, `user_agent` → request context
- `metadata` → additional structured data

This provides an audit trail of authentication behavior.

---

## Auth Actions

The `auth_actions` table tracks endpoint usage.

```sql
auth_actions
```

Key fields:

- `endpoint`, `method` → request signature
- `count` → number of invocations

This is useful for monitoring and rate limiting patterns.

---

## Magic Link Tokens

The `magic_link_tokens` table supports passwordless login via email links.

```sql
magic_link_tokens
```

Key fields:

- `token_hash` → stored token reference
- `user_id` → associated user
- `expires_at` → expiration time
- `used_at` → whether the link has been consumed

Tokens are single-use and time-bound.

---

## System Configuration

The `system_config` table stores dynamic configuration.

```sql
system_config
```

Key fields:

- `key` → configuration name
- `value` → JSON payload
- `updatedBy` → audit reference

This allows runtime configuration without redeploying the system.

---

## Relationships

The main relationships are:

- A user can have many credentials
- A user can have many sessions
- A user can have many auth events
- Magic link tokens belong to a user

All relationships are enforced with foreign keys.

---

## How It Fits Together

A typical authentication flow touches multiple tables:

1. User initiates login
2. Credential or token is verified
3. Session is created
4. Auth event is recorded

On each request:

1. Session is validated
2. User is resolved
3. Roles are applied

The database reflects each step in the process.

---

## Design Principles

The model follows a few principles:

- Identity is separate from credentials
- Sessions are explicit and traceable
- All actions can be audited
- No secrets are stored in plaintext

This structure makes the system easier to reason about and debug.
