# Security Considerations

Seamless Auth is built to run as part of your infrastructure. Security is not handled by an external provider. It is enforced by how your system is configured and how your API applies authentication and authorization.

This section focuses on the decisions that matter when moving from local development to production.

---

## Trust Boundaries

Seamless Auth separates responsibility across three layers:

- Auth server → issues identity and sessions
- API → enforces authentication and authorization
- Frontend → reads state and renders UI

The frontend is not a trusted layer. All security decisions must be enforced by your API.

---

## Sessions and Cookies

Authentication state is stored in HTTP-only cookies.

These cookies should always be configured with:

- HttpOnly → prevents access from JavaScript
- SameSite=Lax or Strict → limits cross-site requests
- Secure → required when using HTTPS

In development, `Secure` may be disabled to allow localhost testing. In production, it must be enabled.

No authentication tokens should be stored in localStorage or sessionStorage.

---

## Cookie Signing

Session cookies are signed by your API.

Requirements:

- Use a strong, randomly generated signing key
- Do not reuse keys across environments
- Do not commit keys to source control

Changing the signing key invalidates all active sessions.

---

## CORS and Origins

Requests flow from browser → API → auth server.

Your API must explicitly allow the correct origin.

In production:

- Do not use wildcard origins
- Match UI origin exactly
- Ensure cookie settings align with origin

Incorrect origin configuration is one of the most common causes of authentication failure.

---

## Passwordless Verification

Seamless Auth relies on short-lived verification mechanisms.

For OTP and similar flows:

- Tokens should expire quickly
- Verification attempts should be limited
- Endpoints should be rate limited

In development, OTP values may be logged. This must not be enabled in production.

---

## Authorization

Authentication identifies the user. Authorization controls access.

Rules:

- Enforce authorization in the API
- Never rely on frontend checks
- Treat missing roles as denied access

Example:

```ts
requireAuth()
requireRole('admin')
```

Unauthorized requests should return `403 Forbidden`.

---

## Defense in Depth

Seamless Auth uses layered security:

- Cookies protect session transport
- Tokens are verified server-side
- Authorization is enforced explicitly
- Roles are part of identity

Each layer reinforces the others.

---

## Development vs Production

Development environments are more permissive.

Common differences:

- OTP values may be logged
- Cookies may not be secure
- Origins are local

Production environments should:

- Require HTTPS
- Use secure cookies
- Disable all debug logging
- Configure real delivery providers
- Restrict allowed origins

The architecture remains the same. Only the constraints change.

---

## Observability

Production systems should record:

- Authentication failures
- Authorization failures
- Suspicious login patterns
- Administrative actions

This data is necessary for auditing and incident response.

---

## Summary

- Enforce all security at the API layer
- Use secure cookie configuration
- Keep signing keys private and rotated
- Define origins explicitly
- Treat development shortcuts as unsafe in production

Seamless Auth provides the primitives. Security depends on how they are applied.
