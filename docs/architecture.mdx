# Architecture Overview

Seamless Auth runs as part of your system. It is not a hosted identity provider.

The auth server, API, and database are all components you deploy and control. Authentication is handled the same way as any other service in your stack.

This page outlines how those components fit together and how authentication state moves through the system.

---

## Core Components

A typical Seamless Auth setup includes four components:

1. **Auth Server**  
   Handles authentication flows, verifies credentials, issues session cookies, and manages identity state.

2. **API Server**  
   Your backend. Validates sessions and enforces authorization rules.

3. **Web Application**  
   The frontend. Initiates authentication and consumes authenticated state.

4. **Database**  
   Stores users, credentials, sessions, and application data.

Each component runs independently and communicates over HTTP using defined interfaces.

## System Topologies

There are two common ways to structure the system.

---

### Pattern 1: Web → Auth → Database

The frontend communicates directly with the auth server.

**Characteristics**

- The auth server verifies credentials and issues HTTP-only cookies
- The database stores users and credential material
- The frontend relies on cookies for authenticated state

**Use Cases**

- Frontend-only applications
- Internal tools
- Prototypes without a backend API

---

### Pattern 2: Web → API → Auth → Database

This is the recommended production model.

**Characteristics**

- The web application communicates only with your API
- The API validates sessions using Seamless Auth middleware
- Authorization is enforced server-side
- The auth server remains the source of identity state
- The web application never accesses the database directly

**Use Cases**

- Applications with business logic
- Role-based access control
- Multi-service systems
- Production deployments

This model keeps authentication centralized and authorization controlled within your API.

## Session Model

Seamless Auth uses HTTP-only cookies to represent authenticated sessions.

**Properties**

- Cookies are not accessible to JavaScript
- Sessions are short-lived and rotated
- Verification happens on the server
- No tokens are stored in localStorage or sessionStorage

This reduces exposure to common client-side attack patterns.

---

## API Authentication Lifecycle

For a protected API route:

1. The browser sends a request with cookies
2. Authentication middleware validates the session
3. A normalized user object is attached to the request
4. Authorization logic checks roles or permissions
5. Business logic executes with a trusted context

Identity is available explicitly at the API layer.

---

## Local vs Production

The architecture does not change between environments.

### Local Development

- Services run via Node.js or Docker Compose
- OTPs may be logged for convenience
- No external providers are required

---

### Production

- Services run in containers or managed compute
- Email and SMS use external providers
- Databases are isolated
- Secrets and configuration are injected securely

The same flow applies in both cases.

---

## Architectural Principles

Seamless Auth is built around:

- Explicit infrastructure
- Inspectable authentication flows
- Server-side authorization
- Consistent behavior across environments
- Minimal hidden behavior

Authentication should be part of your system, not an external dependency.
