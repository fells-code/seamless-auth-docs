# Architecture Overview

Seamless Auth is designed as explicit infrastructure that runs inside your system. It is not a hosted identity provider. The authentication server, API, and database are all visible, deployable components that you control.

This page explains how the system is structured and how authentication state flows between components.

---

## Core Components

A typical Seamless Auth deployment consists of four components:

1. **Auth Server**
   Handles authentication flows, verifies credentials, issues session cookies, and manages identity state.

2. **API Server**
   Your backend application. Validates sessions and enforces authorization rules.

3. **Web Application**
   The frontend. Initiates authentication and consumes authenticated state.

4. **Database**
   Stores users, credentials, sessions, and application data.

Each component runs independently and communicates over HTTP using explicit contracts.

## System Topologies

There are two common deployment patterns.

---

### Pattern 1: Web → Auth → Database

The frontend communicates directly with the auth server.

**Characteristics**

- The web app initiates authentication directly with the auth server
- The auth server verifies credentials and issues HTTP‑only cookies
- The database stores users and credential material
- The frontend relies on browser cookies for authenticated state

**Use Cases**

- Frontend‑only applications
- Prototypes and internal tools
- Systems without a custom backend API

---

### Pattern 2: Web → API → Auth → Database

The recommended production model. The web app talks only to your API.

**Characteristics**

- The web application sends requests only to your API
- The API validates sessions using Seamless Auth middleware
- Authorization is enforced server‑side
- The auth server remains the source of identity truth
- The web application never talks directly to the database

**Use Cases**

- Applications with business logic
- Role‑based access control
- Multi‑service systems
- Production deployments

This model keeps authentication centralized and authorization explicit.

## Session Model

Seamless Auth uses HTTP‑only cookies to represent authenticated sessions.

**Properties**

- Cookies are inaccessible to JavaScript
- Sessions are short‑lived and rotated
- Verification happens server‑side
- No tokens are stored in localStorage or sessionStorage

This reduces exposure to common client‑side attack patterns.

---

## API Authentication Lifecycle

For a protected API route:

1. Browser sends request with cookies
2. Authentication middleware validates session
3. A normalized user object is attached to the request
4. Authorization middleware checks roles or permissions
5. Business logic executes with trusted context

This keeps identity explicit and testable.

## Local vs Production

The architecture remains consistent across environments.

### Local Development

- Services run via Node.js or Docker Compose
- OTPs may log for convenience
- No external delivery provider required

---

### Production

- Services run in containers or managed compute
- Email and SMS use real providers
- Database is isolated in private subnets
- Sessions and secrets are injected securely

The authentication model does not change between environments.

---

## Architectural Principles

Seamless Auth favors:

- Explicit infrastructure
- Inspectable authentication flows
- Server‑side authorization
- Local development parity with production
- Minimal hidden behavior

Identity should be visible and controlled, not abstracted behind a hosted black box.
